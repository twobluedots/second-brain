### 2026-06-19: RAG evaluation pipeline — overall design

**What I decided:** Build a configurable RAG experimentation framework in `experiments/` to measure and improve retrieval quality systematically.

**Why:**
- Long voice recordings with multiple topics are the hardest retrieval case — need numbers to know if changes actually help
- Learning RAG eval concepts (chunking, reranking, embeddings, LLM-as-judge) by building

**Structure:**
```
experiments/
  data/dataset1/
    templates.yaml      ← scenario descriptions per note
    generator.py        ← calls LLM → produces notes.jsonl + eval_set.jsonl
    notes.jsonl         ← synthetic notes (ground truth corpus)
    eval_set.jsonl      ← (query, expected_note_id) pairs
  pipeline/             ← configurable chunker + embedder + retriever (TODO)
  graders/              ← context recall, precision, LLM-as-judge (TODO)
  runner.py             ← config → pipeline → grader → results.db (TODO)
```

**Experiments planned:**
1. Chunking: whole-note vs semantic vs topic-boundary
2. Retrieval: pure vector vs BM25 hybrid vs reranker
3. Embeddings: current default vs text-embedding-3-small vs sentence-transformers

**Grading:** RAGAS for context recall/precision. LLM-as-judge for qualitative scores.

**When to reconsider:** If RAGAS metrics don't correlate with real retrieval quality, supplement with human eval pairs from actual notes.

**RAGAS TestsetGenerator — not suitable for personal notes:** Tried with Ollama. Fails because it expects structured documents with headlines/sections (designed for articles, docs, papers). Personal notes have no structure so the HeadlineSplitter transform breaks. Hand-crafted `eval_set.jsonl` is the right approach for this data type.

### 2026-07-22: Eval set cleanup — removals, fixes, and ambiguous tagging

**What I decided:**
- Removed 6 queries: 2 wrong-topic mappings (devops/pipeline → knowledge graphs note), 1 no-matching-note (laptop), 3 exact duplicates
- Fixed 2 entries: charger query expected note changed from `t_ref_003` (keys/wallet) to `v_ref_001` (actual charger note); temporal "friday" removed from anxious-meeting query
- Tagged 7 queries `"ambiguous": true` — these have multiple equally valid answers in the dataset
- Net: 162 → 156 queries

**Why:**
- Bad mappings inflate failure counts unfairly — model isn't wrong to miss a DevOps query mapped to a knowledge graphs note
- Duplicates inflate the query count and double-weight those specific notes in aggregate metrics
- Ambiguous queries need a different scoring path — a single expected note is meaningless when two notes are equally correct

**Grading decision for ambiguous queries:**
- Excluded from exact metrics (Rank@1, MRR, NDCG) — a single expected note is an arbitrary ground truth
- Scored separately via LLM-as-judge: "is this retrieved note relevant to this query?" — reference-free, no hardcoded valid note list to maintain
- No `also_valid` lists — maintaining them by hand is brittle and doesn't scale as dataset grows

**When to reconsider:** If LLM-as-judge API cost becomes significant at scale, fall back to a semantic similarity threshold (cosine > 0.75 counts as relevant).

## Open questions & future improvements

Things noticed while building that need attention. Actionable — revisit when extending the eval suite.

### Human eval & result inspection

- **`report.py` needs note texts, not just IDs** — showing `v_insight_001` means nothing. Report must show full note text for expected + each retrieved result so you can judge whether a failure is a legitimate model confusion or a bad eval pair.
- **Hard to distinguish two failure types:** (1) model confused two genuinely similar notes — acceptable, signals notes are hard to separate; (2) query is badly written — fix the eval pair not the model. Need to mark these separately when doing human eval.
- **No visual for comparing runs** — currently inspect one run at a time via `report.py`. When multiple experiments exist, need side-by-side comparison. Build a Streamlit page or move to MLflow.
- **Shared data structure between runner and report** — extract an `ExperimentResults` class that owns schema, JSONL loading, and summary/failure methods. Both `runner.py` and `report.py` would import it. Do this after initial results are reviewed and structure feels stable.

### Eval set quality

- **Eval pairs generated by Mistral** — queries may be generic or not match how you'd actually search. After a few weeks of real usage, supplement with real queries.
- **Turkish notes missing** — 5 templates need regeneration with OpenAI. Eval set only covers English until then.
- **Dataset 2 not built yet** — challenging multi-topic dataset (long voice notes with topic shifts). All current experiments test single-topic retrieval only. Dataset 2 is where chunking experiments become meaningful.

### Grading

- **Only recall + precision now** — consider adding: LLM-as-judge (Claude scores relevance 1-5), MRR (Mean Reciprocal Rank, better summary metric across queries)
- **RAGAS metrics not integrated yet** — worth comparing once OpenAI key works

### Experiment scope

- **Only vector retrieval so far** — BM25 hybrid and reranker not implemented. These are most likely to improve recall on short personal notes.
- **Only default embedding** — OpenAI and sentence-transformers variants not wired up yet.
- **MLflow migration** — when 10+ runs exist, JSONL + SQLite becomes limiting. MLflow gives charts and run comparison UI.
