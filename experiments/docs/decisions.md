### 2026-06-19: RAG evaluation pipeline — overall design

**What I decided:** Build a configurable RAG experimentation framework in `experiments/` to measure and improve retrieval quality systematically.

**Why:**
- Long voice recordings with multiple topics are the hardest retrieval case — need numbers to know if changes actually help
- Learning RAG eval concepts (chunking, reranking, embeddings, LLM-as-judge) by building

**Structure:**
```
experiments/
  data/dataset1/
    templates.yaml      ← scenario descriptions per note
    generator.py        ← calls LLM → produces notes.jsonl + eval_set.jsonl
    notes.jsonl         ← synthetic notes (ground truth corpus)
    eval_set.jsonl      ← (query, expected_note_id) pairs
  pipeline/             ← configurable chunker + embedder + retriever (TODO)
  graders/              ← context recall, precision, LLM-as-judge (TODO)
  runner.py             ← config → pipeline → grader → results.db (TODO)
```

**Experiments planned:**
1. Chunking: whole-note vs semantic vs topic-boundary
2. Retrieval: pure vector vs BM25 hybrid vs reranker
3. Embeddings: current default vs text-embedding-3-small vs sentence-transformers

**Grading:** RAGAS for context recall/precision. LLM-as-judge for qualitative scores.

**When to reconsider:** If RAGAS metrics don't correlate with real retrieval quality, supplement with human eval pairs from actual notes.

**RAGAS TestsetGenerator — not suitable for personal notes:** Tried with Ollama. Fails because it expects structured documents with headlines/sections (designed for articles, docs, papers). Personal notes have no structure so the HeadlineSplitter transform breaks. Hand-crafted `eval_set.jsonl` is the right approach for this data type.

**TODO:** Try RAGAS TestsetGenerator separately with proper long structured documents (their docs examples) to learn how it works — not for this project's notes.

### 2026-07-22: Eval set cleanup — removals, fixes, and ambiguous tagging

- Fixed 2 entries: charger query expected note changed from `t_ref_003` (keys/wallet) to `v_ref_001` (actual charger note); temporal "friday" removed from anxious-meeting query
- Tagged 7 queries `"ambiguous": true` — these have multiple equally valid answers in the dataset
- Net: 162 → 156 queries

**Why:**
- Bad mappings inflate failure counts unfairly — model isn't wrong to miss a DevOps query mapped to a knowledge graphs note
- Duplicates inflate the query count and double-weight those specific notes in aggregate metrics
- Ambiguous queries need a different scoring path — a single expected note is meaningless when two notes are equally correct

**Grading decision for ambiguous queries:**
- Excluded from exact metrics (Rank@1, MRR, NDCG) — a single expected note is an arbitrary ground truth
- Scored separately via LLM-as-judge: "is this retrieved note relevant to this query?" — reference-free, no hardcoded valid note list to maintain
- No `also_valid` lists — maintaining them by hand is brittle and doesn't scale as dataset grows

**When to reconsider:** If LLM-as-judge API cost becomes significant at scale, fall back to a semantic similarity threshold (cosine > 0.75 counts as relevant).

### Human eval & result inspection

- **`report.py` needs note texts, not just IDs** — showing `v_insight_001` means nothing. Report must show full note text for expected + each retrieved result so you can judge whether a failure is a legitimate model confusion or a bad eval pair.
- **Hard to distinguish two failure types:** (1) model confused two genuinely similar notes — acceptable, signals notes are hard to separate; (2) query is badly written — fix the eval pair not the model. Need to mark these separately when doing human eval.
- **No visual for comparing runs** — currently inspect one run at a time via `report.py`. When multiple experiments exist, need side-by-side comparison. Build a Streamlit page or move to MLflow.
- **Shared data structure between runner and report** — extract an `ExperimentResults` class that owns schema, JSONL loading, and summary/failure methods. Both `runner.py` and `report.py` would import it. Do this after initial results are reviewed and structure feels stable.

- **Turkish notes missing** — 5 templates need regeneration with OpenAI. Eval set only covers English until then.

Not acted on — parked until these rows are shown to be meaningfully skewing retrieval numbers.

### Grading

- **Only recall + precision now** — consider adding: LLM-as-judge (Claude scores relevance 1-5), MRR (Mean Reciprocal Rank, better summary metric across queries)
- **RAGAS metrics not integrated yet** — worth comparing once OpenAI key works

### Experiment scope

- **Only vector retrieval so far** — BM25 hybrid and reranker not implemented. These are most likely to improve recall on short personal notes.

### 2026-08-03: Ask-service eval — split monolith, new `ask_eval/` folder

**What I decided:** Retired the `eval_ask.py` monolith (single script that ran live `ask()` calls, then RAGAS scoring, then save — all in one pass) into a runner/grader split, and gave it its own folder: `experiments/ask_eval/` (`runner.py` done, `grader.py` next), instead of adding more flat `eval_ask_*` files to `experiments/`.

**Why:**
- `eval_ask.py` coupled an expensive step (5 live `ask()` calls) to a fragile one (RAGAS) with no save in between — every RAGAS crash meant re-running the pipeline calls from scratch.
- `runner.py` now writes each record to disk immediately after calling `ask()`; grading against saved records is a separate, rerunnable step that costs judge calls only.
- Separate folder, not flat files: this eval tests a different layer than the existing retrieval-only `runner.py`/`grader.py`/`report.py` (flat in `experiments/`) — full pipeline (retrieve + generate) against live `Storage`, reference-free RAGAS metrics (faithfulness, answer_relevancy) instead of ground-truth recall/mrr. `ask_eval/` makes that distinction visible in the file structure instead of implicit.

### 2026-08-06: Index rebuilt once per run, not once per query; index staleness fix

**What I decided:**
- `pipeline.retrieve()` now takes a pre-built `collection` instead of deriving it from `config` on every call. `runner.py` calls `pipeline.index.load_or_build(config)` once before the query loop and passes the same `collection` into every `retrieve()` call.
- `get_index_path()` in `pipeline/index.py` now includes a hash of `notes.jsonl`'s content in the index directory name (`{dataset}__{notes_hash}__{embedding_model}`), not just dataset + embedding model names.
- Extracted `hash_file()` (SHA-256, first 8 hex chars) into a new `experiments/utils.py`, shared by `eval_set_hash` (in `runner.py`) and the new `notes_hash` (in `pipeline/index.py`) — one helper instead of duplicating it per file.

**Why:**
- `retrieve()` was calling `load_or_build()` — a fresh `chromadb.PersistentClient` + `get_or_create_collection()` — on every single query (155× per run). The index already existed on disk so no re-embedding happened, but every call paid full reconnect overhead for no reason. Building the collection once per run and reusing the handle fixes this.
- Separately, and more importantly: the old index path (`{dataset}__{embedding_model}`) was derived only from names, never from `notes.jsonl`'s content. Editing `notes.jsonl` (e.g. regenerating notes) would silently leave `load_or_build()` returning the *stale* on-disk collection forever — `collection.count() > 0` short-circuits before ever checking whether the notes actually changed. That's a silent correctness bug, not just noise: retrieval would be scored as if against current notes while actually querying old embeddings. Hashing `notes.jsonl` into the path means any edit produces a path the code has never seen, so it rebuilds automatically.
- Old index directories (`dataset1__default`, `dataset1__bge-large`) are now orphaned under the new naming — left on disk, not deleted; harmless and cheap to leave.

### 2026-08-07: `ask_eval/grader.py` — generation metrics added (faithfulness, answer_relevancy)

**What I decided:**
- Added `Faithfulness` + `AnswerRelevancy` (both from `ragas.metrics.collections`, same family as the existing `ContextRelevance`/`ContextUtilization`) to `grader.py`, bringing it to four metrics total — two retrieval-side, two generation-side, scored per record and averaged.
- `AnswerRelevancy` needs an embeddings model; used `OpenAIEmbeddings(model="text-embedding-3-small")` — cheap, and reuses the `AsyncOpenAI()` client already in the file. (`ragas.embeddings.embedding_factory` exists but is deprecated in favor of the provider classes.)
- Bumped the judge LLM's `max_tokens` from RAGAS's default 1024 to 4096. Faithfulness decomposes the response into atomic claims before verifying each against the contexts — a synthesis-style answer (e.g. "most important wins from last month," pulling from several notes) decomposes into enough claims that the JSON output was hitting the old cap and getting truncated mid-response.
- Both new metrics reuse the existing "skip if `response` is empty" guard already in place for `context_utilization` — nothing to judge on an empty response.
- Also corrected `eval-ask-grader.md`'s session-1 naming (it said `ContextPrecisionWithoutReference`, actually shipped as `ContextRelevance` + `ContextUtilization`) and updated its "done when" checklist from three metrics to four.

**Why:** this is Session 3 of the plan already ratified in `eval-ask-grader.md` (2026-08-03) — read retrieval and generation scores together (the "triangle" table in that doc) to tell whether a bad answer is a retrieval failure or a generation failure, rather than tuning either side blind.

**Known limitation, not yet acted on:** faithfulness's claim-level entailment check verifies individual facts against context, but doesn't judge synthesis/ranking quality (e.g. "most important" is a selection judgment, not a checkable claim) — suspect it under-evaluates multi-note aggregation answers. `eval-ask-grader.md`'s parking lot already earmarked dumping the decomposition output to check this before touching any judge prompts.

### 2026-08-07: `ask_eval/grader.py` — scoring parallelized

**What I decided:** `_score_record` now fires its up-to-4 metric calls concurrently via a new `_run_scorer()` wrapper + `asyncio.gather`, instead of awaiting them one at a time; `grade()` gathers all records concurrently too instead of a sequential list comprehension. A single `asyncio.Semaphore(5)`, shared across every scorer call, caps concurrency; `_run_scorer()` also keeps the existing per-metric try/except-and-warn behavior intact.

**Why:** the sequential version made up to ~20 serial judge calls for a 5-question run, each a multi-second round trip — nothing about one record's or one metric's score depends on another, so full concurrency is safe; the semaphore exists only to avoid OpenAI rate limits, not a data dependency.

**Verified:** live run via `python -m experiments.ask_eval.grader` completed in ~34s, no rate-limit errors, no truncation warnings.

### 2026-08-12: `ask_eval/grader.py` — faithfulness decomposition surfaced

**What I decided:**
- Added `FaithfulnessWithDecomposition`, a subclass of ragas's `Faithfulness` that calls the same private steps `ascore()` already runs internally (`_create_statements`, `_create_verdicts`, `_compute_score`) but returns the per-claim breakdown alongside the score instead of discarding it — no extra LLM calls.
- Returns `(MetricResult, decomposition)` from a new `ascore_with_decomposition()` method rather than stashing state on `self`, since one scorer instance is shared across concurrent record scoring (`asyncio.Semaphore(5)`) — an instance attribute would have been a race condition.
- Each record's result now carries `faithfulness_decomposition`: a list of `{statement, verdict, reason}`, saved to `scores/*.json` alongside the existing scores. Not printed to console — JSON only, to keep console output short.

**Why:** this is the parking-lot item flagged in the 2026-08-07 entry above — faithfulness's claim-level check doesn't judge synthesis/ranking quality, and the decomposition needed to be inspectable before touching any judge prompts to fix that.

**Approach considered and rejected:** reimplementing statement generation + NLI verdicting ourselves, for full control and no coupling to ragas internals. Rejected — duplicates logic ragas already runs, risks drifting from ragas's actual scoring behavior, and the private methods used here (`_create_statements`, `_create_verdicts`, `_compute_score`) are stable enough for an eval script. Tradeoff: an unannounced ragas upgrade could rename or change these methods; worth a quick check next time `ragas` version bumps in `pyproject.toml`.

**Next:** actually read the decomposition output from a real run to check the aggregation-judgment hypothesis, then decide whether it warrants a judge-prompt change.

### 2026-08-21: Dataset2 — ask-aware eval pilot (templates2.yaml)

**What I decided:** Built a second, parallel synthetic eval corpus — `templates2.yaml` → `generator2.py` → `notes2.jsonl`/`eval_set2.jsonl` — covering `mood`/`journal`/`task`/`achievement` (zero coverage in dataset1's `templates.yaml`). Query hints are split into `query_hints_search` (dataset1-style, tests plain retrieval) and `query_hints_ask` (natural questions, carries `intent`/`expected_time_filter`/`expected_category_filter`/`expected_note_ids` so `analyzer.py`'s extraction can eventually be scored, not just retrieval). Kept as a fully separate `generator2.py` rather than modifying `generator.py`, so dataset1 stays independently reproducible — matches the existing `ragas_generate.py`/`ragas_testset/generate.py` pattern of parallel generators for different eval strategies.

**Why:**
- Dataset1's hints only ever exercised the Search page path; nothing tested the Ask pipeline's analyzer stage at all
- Real `ask_log` (28 logged queries, checked before writing hints) showed `category_filter` populated in 0/28 and `time_filter` in only 4/28 — very different from the filter-heavy "how did I feel lately" mental model assumed going in. Ask hints were calibrated to that reality: mostly null filters, 2 deliberate filter-testing probes
- `analyzer.py`'s `pattern` intent is inherently many-notes-to-one-query (recurrence = separation in time), so a single `expected_note_id` couldn't represent it — added `expected_note_ids` as a list, plus a `days_ago` relative-offset field (not absolute dates, so the corpus doesn't go stale) so pattern examples could be built for real: Sunday-dread recurring across separate weeks (`v2_journal_002/002b/002c`), and a habit streak within the current week (`v2_ach_002/002b/002c`)

**Scope decision:** pilot only — 30 templates across the 4 missing categories, not a rewrite of dataset1's existing ~40. Building the actual stage-isolated eval scripts (analyzer-only / retrieval-only / generation-only scoring) that consume this schema is explicitly deferred — tracked in `docs/roadmap.md` under "Retrieval quality & eval." This task produced the data only.

**Prompt-tuning, worth remembering:** first generation pass (temperature 0.9, no examples) came out melodramatic — 11/11 voice notes used an ellipsis, register like "I can't breathe," "bam, everything at once." Lowering temperature alone (0.6) did not fix it — same drama, same 3/3 ellipsis rate on the retest sample. What worked: few-shot examples of the actual flat/plain register in the prompt (not "avoid X" negative instructions, which don't work well and risk priming toward the named example), plus dropping the explicit "an ellipsis is fine if it trails off" permission sentence entirely — the model was over-triggering on that instruction even when the few-shot examples themselves never used one. Final state: 3/11 voice notes use an ellipsis, no "ADHD" label anywhere in generated text (replaced with described tendencies per the spec), no emoji.

**Also corrected mid-task:** the voice-note prompt originally claimed transcripts come through a repunctuation cleanup step — checked `src/processing.py` and that's wrong, production is raw `whisper.transcribe()` with no cleanup (`experiments/pipeline/repunctuate.py` is a separate, not-yet-integrated research experiment). Whisper's raw output can legitimately include an ellipsis for trailing/unclear speech, so the prompt was corrected to reflect that instead of banning ellipses outright.

**When to reconsider:** if the pilot's 4 categories prove useful once the eval harness (deferred above) actually scores against them, extend the same schema to dataset1's remaining ~26 templates (insight/reference/learning) in a follow-up task.

### 2026-08-24: Dataset2 stage-aware reporting — design (`experiments/reporting/`)

**What I decided:**
- New `experiments/reporting/` package split by function, not by stage: `summarize.py` (rows → dict, pure), `compare.py` (two row-sets → dict, pure), `print.py` (dict → terminal text). `experiments/report.py`/`experiments/compare.py` keep their existing invocation paths and delegate to it via a new `--stage {retrieval,intent,generation}` flag on dataset2 rows; omitted → every stage present in the run prints. Dataset1's existing behavior is untouched.
- Compare rule: a stage is only comparable between two runs if it was actually computed in both — hard requirement for retrieval/intent (error clearly, never print an empty/misleading table). Generation is the deliberate exception: comparable across runs regardless of whether context came from gold notes or a retriever, since "given this context, how good is the answer" stays well-defined either way. Comparing a gold-context-only run against a full-pipeline run on generation metrics is a first-class use case, not something to reject — it's how retrieval's downstream impact gets measured indirectly.
- Intent reporting surfaces per-class confusion (`expected_intent → actual_intent` counts), not just aggregate accuracy. Generation reporting surfaces a low-score count (`< 0.5`) alongside each metric's mean. Both because an average alone hides exactly the failure pattern worth seeing (which classes get confused; a few badly hallucinated answers buried in an otherwise-good mean).
- Row matching for compare stays keyed by `query` text, same convention already used in dataset1's `compare.py` — no new join key.
- Written up as a spec first (`experiments/docs/dataset2-stage-reporting.md`) rather than implementing directly — 8 decisions, over the usual 3-decision single-task threshold. Split into two implementation tasks: 4a (summarize + print + `report.py` wiring), 4b (compare + `compare.py` wiring).

**Why:**
- `report.py`/`compare.py` predate dataset2's multi-stage, sparse-column `stage_results` schema — they assume every row has the same shape (single `expected_id`, single `recall`/`mrr`). That breaks once rows can have any subset of {retrieval, intent, generation} populated depending on which stages a config selected.
- Considered a folder split by stage instead (`retrieval.py`/`intent.py`/`generation.py`, each self-contained) — rejected in favor of by-function, since the goal is keeping the print layer cheaply swappable later (pandas/SQL/notebook, not built now) and keeping formatting consistent across stages by construction; by-stage would mean pulling print logic out of three files later instead of deleting one.
- Folder can't be named `report/` — collides with the existing `experiments/report.py` module path.

**Next:** implement Step 4a, verify against a dataset2 intent+retrieval run and a gold-context generation run per the spec's acceptance checks, then 4b.

### 2026-08-24: `runner.py` fixed — generation-stage eval no longer scores browse-intent rows with answer_relevancy

**What I decided:** In `experiments/runner.py`, the generation stage now checks `gen_plan.intent != "browse"` before calling `generate_answer()`/`grade_generation()`. Browse-intent rows keep their `generated_answer=None` default, which `report.py` already excludes from the generation summary — no changes needed there or in `grader.py`.

**Why:** `dataset2_generation_20260824-121145` showed high faithfulness (mean 0.933) but low answer_relevancy (mean 0.510, 27/56 rows flagged low). Traced it to a scope mismatch, not a real quality problem: `src/rag/analyzer.py` already classifies "show me X" / "list X" queries as `browse`, and production `src/rag/pipeline.py` short-circuits that intent — it returns raw notes with `answer=None` and never calls the generator at all. But the generation-stage eval harness (`experiments/pipeline/generation.py` + `runner.py`) was building a `QueryPlan` from gold/live intent and calling `generate()` unconditionally for every `ask` row, including ones gold-labeled `browse`. RAGAS's `AnswerRelevancy` metric (`grader.py`) works by having an LLM reverse-generate questions from the answer and comparing embeddings against the original query — a narrative answer to an imperative "show me..." query mismatches in phrasing even when the content is fully faithful, which is exactly what tanked the score. Paired same-note comparisons confirmed it: "how do I feel in loud crowded places" scored 0.916, "show me notes about feeling overwhelmed" (identical source note) scored 0.293.

**What I tried first:** Initially suspected the RAGAS metric itself was just noisy/unsuited to short queries. Reading `grader.py`'s actual RAGAS call plus the paired-query pattern in the report ruled that out — the metric is doing what it's designed to do, just being pointed at rows it was never meant to score.

**Trade-offs:**
- ✅ Generation-stage summary now only reflects query types production actually sends to the generator
- ✅ No change to production code or to the intent classifier — both were already correct
- ❌ Browse-intent rows lose generation-quality signal entirely in this stage; if browse's "list the notes" behavior ever needs a different quality check, it'll need its own metric, not answer_relevancy

**When to reconsider:** If browse intent's raw-note-listing behavior needs its own eval signal (e.g. "are the right notes shown"), design a separate check for it rather than reusing answer_relevancy.

### 2026-08-24: Dataset2 intent labels corrected (qa/factual/pattern) — classifier non-determinism found, unresolved

**What I decided:** Fixed 11 mislabeled `intent`/`expected_time_filter` values in `templates2.yaml`, synced the same fixes into `eval_set2.jsonl`:
- 7 rows relabeled `qa` → `factual` (single stored-fact lookups — "what deadline did I write down", "what was that thing I wanted to look into", "what did someone say that stuck with me", "what was that message I kept meaning to deal with", "what did I finish that had been open for months", "what did I say about something that used to be hard", "when did I start doing the habit this week") — these match `analyzer.py`'s own `factual` examples almost verbatim
- `v2_journal_002` "what do I usually feel before the week starts": `qa` → `pattern`
- `v2_ach_002` "have I kept the streak going this week": `pattern` → `qa`
- `t2_mood_002` "have my mornings been better or worse lately": `expected_time_filter` `this_week` → `null` — query says "lately", not one of the three exact windows `analyzer.py`'s own prompt requires; the row contradicted the documented time_filter rule

**Root cause:** `templates2.yaml`'s header comment calibrated the ask-hint intent mix off 28 real logged queries that only ever used `browse`/`qa`/`pattern` — `factual` never appeared in that sample, so it dropped out of the mental model while hand-authoring hints even though `analyzer.py` has always defined 4 intents (verified via git history — `factual` was never merged into `qa` in code, only in the eval labels). Not a deliberate taxonomy decision, a labeling oversight surfaced by `dataset2_intent_20260824-120557_intent_report.txt`'s `qa → factual` mismatches, which looked like classifier confusion but were mostly correct classifications against wrong ground truth.

**Found in the process — not fully resolved:**
- **Classifier non-determinism at temperature=0.** Two back-to-back identical eval runs (`dataset2_intent_20260824-192056`, `-192309`; same config, same eval set) produced different `factual`/`qa` accuracy: 0.821 vs 0.857. `analyzer.py`'s OpenAI call sets `temperature=0` (`gpt-4o-mini`) but the `factual`/`qa` boundary specifically flips run to run. A single run's accuracy number for this stage isn't trustworthy alone.
- Several rows landed on `factual` only after real back-and-forth (e.g. "when did I start doing the habit this week", "what did someone say that stuck with me") — defensible as `qa` too, and the classifier's own non-determinism on this exact boundary (above) suggests the line between them may not be a clean one.
- `v2_ach_002`'s relabel to `qa` now contradicts the 2026-08-21 entry above and `templates2.yaml`'s own header comment, both of which cite it as a worked example of `pattern`-intent aggregation across 3 notes (`v2_ach_002/002b/002c`). Header comment not yet updated to match.

**Open question, deliberately not decided now:** whether `factual` should exist as a separate intent from `qa` at all — analyze later once more real usage data or eval runs exist, rather than ratifying a labeling rule off this one pass.

**When to reconsider:** before trusting future `factual`/`qa` intent-eval numbers, run the intent stage N times and average (single-run numbers aren't reliable given the non-determinism above). Update `templates2.yaml`'s header comment once `v2_ach_002`'s reclassification is confirmed final.
