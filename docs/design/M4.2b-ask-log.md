# [M4.2b] ask_log — spec

**Date:** 2026-07-13 (drafted evening before; confirm decisions at session start 2026-07-14)
**Timebox:** one morning block (spec confirm ~15 min → test → implement → shakedown after)

## Goal
Every Ask interaction (success or failure) is recorded in a new `ask_log` SQLite table, so real usage builds the eval dataset for generation-quality experiments.

## Non-goals (→ parking lot)
- 👍/👎 answer rating on the Ask page — future ground truth for generation evals, separate UI task
- Any analytics/reporting UI over ask_log — the eval track consumes it via SQL/scripts
- Logging token counts or cost — add later if cost tracking becomes a question

## Decisions
Agreed in principle 2026-07-13, confirm tomorrow:
- [x] **Separate `ask_log` table**, not an extension of `search_log` — shapes differ too much (search_log = filter usage; ask_log = question → plan → retrieval → answer)
- [x] **Fields:** `id, query, input_type (text/voice), intent, time_filter, category_filter, k, retrieved_note_ids (JSON), answer, result_count, error (nullable), created_at`
- [x] **Failures are logged too** — row with `error` filled; failed asks are prime eval cases
- [x] **Logging call lives in the ask orchestration flow**, not storage.save — same pattern as `log_category_event` (M2.3); storage exposes a dumb `log_ask_event()`
- [x] **Model provenance: yes** (2026-07-14) — two nullable TEXT columns `analyzer_model`, `generator_model` (e.g. `"openai:gpt-4o-mini"`). Provider chain means answers come from different models; eval needs to know which model wrote/routed each one.
- [x] **Latency: yes, in the table** (2026-07-14) — three INT columns `analyzer_ms`, `retrieval_ms`, `generation_ms`. In the table (not only log files) because the purpose is *analytical* (SQL: avg latency by stage/model, the bge-large speed question), not operational debugging. App.log still gets the usual INFO line per standards.
- [x] **retrieval_fallback: added in code review** (2026-07-15) — INTEGER 0/1 (SQLite has no bool; Python API takes a real bool). Persists `AskResult.fallback`: retrieval found nothing with the plan's filters and retried unfiltered, returning closest notes. Without it a weak-match ask looks like a healthy `result_count=2` row — it flags exactly the degraded asks eval wants.

## How to read failure modes from a row
| Signal | Meaning |
|---|---|
| `error` filled | whole pipeline crashed — exception text; other fields best-effort |
| `analyzer_model` NULL | analyzer LLMs failed → default plan (qa, k=8) was used |
| `generator_model` NULL, `result_count` > 0 | generation LLMs failed → plain note-list fallback shown |
| `generator_model` NULL, intent = browse | normal — browse never generates |
| `retrieval_fallback` = 1 | no real match — answer built on "closest available" notes |
| exact exception details | app.log (WARNING lines) — logs answer *what happened*, this table answers *which asks were degraded* |

**Migration note:** the column was added after the table shipped; existing DBs need `scripts/migrate_ask_log_retrieval_fallback.py` (CREATE TABLE IF NOT EXISTS never alters — see bugs.md 2026-07-16 silent-logging entry).

## Acceptance checks
1. Ask a question on the Ask page → `sqlite3` shows one ask_log row with intent, retrieved ids, and the answer text.
2. Force a failure (e.g. providers unreachable) → row exists with `error` filled, other fields as far as known.
3. Browse intent (no generation) → row logged with `answer` null, retrieved ids present.
4. pytest: `storage.log_ask_event()` round-trip test passes (written by me, before implementation).
