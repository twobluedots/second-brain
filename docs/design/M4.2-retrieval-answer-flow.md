# M4.2 — Retrieval & Answer Generation Flow

## What we're building

A new **Ask** page where the user can query their notes in natural language (text or voice) and get a generated answer — not a list of raw transcriptions.

This is the missing piece of the MVP: capture works, but retrieval is broken without answer synthesis.

---

## Two distinct use cases

**1. Factual lookup** — "where did I put my car manual?"
→ retrieve 1-3 best-match notes → LLM writes a one-sentence answer, cites source note

**2. Open question / synthesis** — "what have I been stressed about lately?"
→ retrieve top-k notes → LLM synthesizes a paragraph answer with sources

Browse/filter (show me all tasks, notes from this week) stays on the existing Search page — that's a different mental mode.

---

## Full pipeline

```
query (text or voice)
    ↓
[if voice] Whisper transcription → text
    ↓
LLM call #1: query analyzer
    returns: { intent, filters, k }
    ↓
Retrieval (using filters + k)
    ChromaDB semantic search + SQLite metadata filters
    ↓
Code check:
    - browse intent OR no/weak results → skip LLM, return list or no-match
    ↓
LLM call #2: generation
    receives: { intent + retrieved notes }
    intent tells it how to format the output
    ↓
Response
```

Two LLM calls maximum per query. Intent is decided once in call #1 and passed through as context to call #2.

---

## Intent types

| Intent | Triggered by | K | Generation |
|---|---|---|---|
| factual | specific named thing (manual, recipe, address) | 3–5 | 1-sentence answer + source citation |
| QA | question words (what, how, why, ?) | 5–10 | paragraph answer + sources |
| pattern | aggregation words (lately, this month, how have I been) | 15–20 | summary paragraph + N sources |
| browse | show me / list / find all | all in filter | no LLM, return list |

---

## Query analyzer output (LLM call #1)

```json
{
  "intent": "factual | QA | pattern | browse",
  "time_filter": null | "today" | "this_week" | "this_month",
  "category_filter": null | "mood" | "task" | "learning" | ...,
  "content_type": null | "voice" | "image" | "text",
  "k": 5
}
```

Why LLM (not heuristics): voice queries will be messy and casual. Regex breaks on "um what was that thing I was learning last week." One structured LLM call handles it cleanly.

---

## Generation decision (after retrieval)

```
if browse intent → no LLM, return list directly
if results empty or weak → no LLM, return 1-2 closest + "couldn't find a clear match"
otherwise → LLM call #2 with { intent + notes }
```

The generation LLM uses intent as a prompt instruction to format the output correctly. No second routing decision — intent travels through from call #1.

---

## No-match behavior

Return 1-2 closest notes with a disclaimer: "Couldn't find a clear match, but these might be relevant."
Don't dead-end the user.

---

## Pattern queries

- Large k (15–20) + category filter if detectable
- No pre-generated summaries at save time (premature optimization at current note volume)
- If too few notes for a pattern: "Not enough notes on this topic yet" instead of hallucinating

---

## Input: text + voice

Both are equally important. Voice → Whisper → text before query analysis. Same pipeline from there.

---

## What's NOT in scope here

- Tags — discover whether needed after real usage of this flow
- Agentic approach (LLM picks tools) — explicit routing is more predictable for MVP; natural upgrade path when queries get more complex
- Pre-generated summaries at save time — parking lot until scale demands it
- Pattern queries of type "what keeps coming up" (aggregation across all notes) — too complex for now

---

## Embedding model change (prerequisite)

Switching ChromaDB from default `all-MiniLM-L6-v2` to `bge-large-en-v1.5`:
- Rank@1: 61% → 72%, Avg Precision: 0.698 → 0.783 (from experiments)
- `sentence-transformers` already installed
- Requires wiping `chroma_data/` and re-indexing from SQLite (safe — SQLite is source of truth)
- Apply `query_instruction` prefix at query time (per experiment next steps)
